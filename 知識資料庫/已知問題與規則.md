# 已知問題與規則（共用錯誤記憶）

## 這份文件的用途

這是全部 AI 代理共用的一份「教訓清單」。目的是解決使用者最頭痛的問題：**工具改壞了不知道、同樣的錯誤重複發生**（2026-09-14 grill-me 訪談，`context/about-me.md` top_pain）。

每一位代理，不管用哪個模型（Gemini／ChatGPT／Claude），開始任務前都會讀到這份文件。規則很簡單：

1. **檢查代理**確認一個真實問題（不是誤判）之後，必須依下面的格式，把它新增一條到「已確認問題」清單。
2. 任何代理（包含檢查代理自己）在動手前，**先看這份清單有沒有相關項目**，避免重複犯同一個錯，或用同一個錯誤的做法。
3. 條目只增加、不刪除，除非使用者確認這個問題已經徹底解決且不會再發生——這時候把它移到「已解決」區塊並保留原始記錄，不要直接刪掉。
4. 使用繁體中文、寫清楚「發生在哪裡」「錯在哪裡」「以後要怎麼避免」，不要只寫「有 bug」。

## 記錄格式

```
### 【日期】簡短標題
- 發生階段／代理：
- 問題描述：
- 根本原因：
- 以後要怎麼避免：
- 確認者：
```

## 已確認問題

### 【2026-09-15】Gemini 顯示「額度不足」不代表 AI Studio 儀表板的「總用量」很高，兩者是不同的量測基準
- 發生階段／代理：AI 工作台／啟動全隊，供應商選 Gemini 時
- 問題描述：介面顯示「額度不足」，但打開 Google AI Studio 的用量儀表板看，用量少到不合理，兩邊數字對不起來，讓人懷疑是不是錯誤訊息本身寫錯。
- 根本原因：HTTP 429 背後至少有兩種完全不同的限制：「每分鐘」的短時間請求數限制（很容易被連續幾次呼叫或重試打到，跟當日/當月總用量無關），以及「每日」的免費額度上限（可能遠比想像中低）。Google 的錯誤回應其實有把這兩種區分開來（`error.details` 裡的 `quotaId` 會標 `PerMinute` 或 `PerDay`），但舊版程式碼完全沒讀這個欄位，429 一律講成同一句「額度不足」，才會讓人誤以為儀表板的總用量跟錯誤訊息矛盾——其實兩者本來就是在量不同的東西，不衝突。
- 以後要怎麼避免：任何代理如果要處理外部 API 的錯誤訊息（不只 Gemini），優先解析 API 回應裡的結構化錯誤欄位（例如這裡的 `error.details`），不要只憑 HTTP 狀態碼或一句話訊息就套用固定文案；狀態碼相同不代表原因相同，把不同原因混成同一句話，使用者會覺得系統在說謊。
- 確認者：使用者實測回報（2026-09-15），由本次 Claude session 解析 Google 官方文件的 429 錯誤結構後確認並修正（見 `index.html` 的 `解析Gemini配額診斷` 函式）。
